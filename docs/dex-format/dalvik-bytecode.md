# Dalvik bytecode format

## General design

- The machine model and calling conventions are meant to approximately imitate common real
  architectures and C-style calling conventions:
    - The machine is register-based, and frames are fixed in size upon creation. Each frame consists
      of a particular number of registers (specified by the method) as well as any adjunct data
      needed to execute the method, such as (but not limited to) the program counter and a reference
      to the `.dex` file that contains the method.
    - When used for bit values (such as integers and floating point numbers), registers are
      considered 32 bits wide. Adjacent register pairs are used for 64-bit values. There is no
      alignment requirement for register pairs.
    - When used for object references, registers are considered wide enough to hold exactly one such
      reference.
    - In terms of bitwise representation, `(Object) null == (int) 0`.
    - The *N* arguments to a method land in the last *N* registers of the method's invocation frame,
      in order. Wide arguments consume two registers. Instance methods are passed a `this` reference
      as their first argument.
- The storage unit in the instruction stream is a 16-bit unsigned quantity. Some bits in some
  instructions are ignored / must-be-zero.
- Instructions aren't gratuitously limited to a particular type. For example, instructions that move
  32-bit register values without interpretation don't have to specify whether they are moving ints
  or floats.
- There are separately enumerated and indexed constant pools for references to strings, types,
  fields, and methods.
- Bitwise literal data is represented in-line in the instruction stream.
- Because, in practice, it is uncommon for a method to need more than 16 registers, and because
  needing more than eight registers *is* reasonably common, many instructions are limited to only
  addressing the first 16 registers. When reasonably possible, instructions allow references to up
  to the first 256 registers. In addition, some instructions have variants that allow for much
  larger register counts, including a pair of catch-all `move` instructions that can address
  registers in the range `v0` – `v65535`. In cases where an instruction variant isn't available to
  address a desired register, it is expected that the register contents get moved from the original
  register to a low register (before the operation) and/or moved from a low result register to a
  high register (after the operation).
- There are several "pseudo-instructions" that are used to hold variable-length data payloads, which
  are referred to by regular instructions (for example, `fill-array-data`). Such instructions must
  never be encountered during the normal flow of execution. In addition, the instructions must be
  located on even-numbered bytecode offsets (that is, 4-byte aligned). In order to meet this
  requirement, dex generation tools must emit an extra `nop` instruction as a spacer if such an
  instruction would otherwise be unaligned. Finally, though not required, it is expected that most
  tools will choose to emit these instructions at the ends of methods, since otherwise it would
  likely be the case that additional instructions would be needed to branch around them.
- When installed on a running system, some instructions may be altered, changing their format, as an
  install-time static linking optimization. This is to allow for faster execution once linkage is
  known. See the associated
  [instruction formats document](https://source.android.com/docs/core/runtime/instruction-formats)
  for the suggested variants. The word "suggested" is used advisedly; it is not mandatory to
  implement these.
- Human-syntax and mnemonics:
    - Dest-then-source ordering for arguments.
    - Some opcodes have a disambiguating name suffix to indicate the type\(s\) they operate on:
        - Type-general 32-bit opcodes are unmarked.
        - Type-general 64-bit opcodes are suffixed with `-wide`.
        - Type-specific opcodes are suffixed with their type (or a straightforward abbreviation),
          one of: `-boolean` `-byte` `-char` `-short` `-int` `-long` `-float` `-double` `-object`
          `-string` `-class` `-void`.
    - Some opcodes have a disambiguating suffix to distinguish otherwise alike operations that have
      different instruction layouts or options. These suffixes are separated from the main names
      with a slash ("`/`") and mainly exist at all to make there be a one-to-one mapping with static
      constants in the code that generates and interprets executables (that is, to reduce ambiguity
      for humans).
    - In the descriptions here, the width of a value (indicating, e.g., the range of a constant or
      the number of registers possibly addressed) is emphasized by the use of a character per four
      bits of width.
    - For example, in the instruction "`move-wide/from16 vAA, vBBBB`":
        - "`move`" is the base opcode, indicating the base operation (move a register's value).
        - "`wide`" is the name suffix, indicating that it operates on wide (64 bit) data.
        - "`from16`" is the opcode suffix, indicating a variant that has a 16-bit register reference
          as a source.
        - "`vAA`" is the destination register (implied by the operation; again, the rule is that
          destination arguments always come first), which must be in the range `v0` – `v255`.
        - "`vBBBB`" is the source register, which must be in the range `v0` – `v65535`.
- See the
  [instruction formats document](https://source.android.com/docs/core/runtime/instruction-formats)
  for more details about the various instruction formats (listed under "Op & Format") as well as
  details about the opcode syntax.
- See the [`.dex` file format document](https://source.android.com/docs/core/runtime/dex-format) for
  more details about where the bytecode fits into the bigger picture.

### Dalvik odex instructions details

**`execute-inline` and `execute-inline/range` (`35mi`, `3rmi`).** `BBBB` indexes the inline-method
table of built-in implementations instead of the method pool; the argument registers and the word
count are the invoke ones, with at most four argument words. The result (if any) is fetched by a
`move-result*` instruction, as for any invoke.

**The quick field family (`22cs`).** `CCCC` is the byte offset of the instance field from the start
of the object instead of a field reference; the offset fits 16 bits. The typed `iget` / `iput`
variants all use the six untyped quick opcodes.

**The quick invoke family (`35ms`, `3rms`).** `BBBB` is a vtable index instead of a method
reference. `invoke-virtual-quick` indexes the receiver's vtable; `invoke-super-quick` indexes the
vtable of the current method's class's superclass.

**`invoke-direct-empty` (`35c`, API 1–13).** Invokes a direct method whose body is empty – in
practice `Object.<init>()V` – without the call.

**`invoke-object-init/range` (`3rc`, API 14–20).** Performs `Object.<init>` on the indicated object
without calling the empty method, and marks the object finalizable. The argument count is `1` and
the third code unit holds the object register.

**The volatile family (`21c`, `22c`, API 9–20).** Field loads and stores with volatile (ordered)
access semantics; the 64-bit forms are atomic.

**`return-void-barrier` (`10x`, API 11–20).** Returns from a `void` method after a store barrier.

**`throw-verification-error` (`20bc`, API 5–20).** Always throws the exception implied by the
recorded verification failure: `AA` carries the 6-bit failure code and the 2-bit reference kind,
`BBBB` the failing reference.

**`breakpoint` (`ec`).** Replaces the first code unit of another instruction and restores it when
executed, leaving no trace of itself; it never appears in a file.

## dex `009` / `013` bytecode set

The dex versions `009` and `013` define 223 instructions and the two switch payload tables, plus the
install-time odex forms in `ee`, `f0` and `f2`–`fb`. Op values are hexadecimal. Where the two
versions differ, the `013` value follows the `009` value after a slash in the `Op & Format` column;
the `013` numbering leaves `2d` and `73` unused, advancing `cmpl-float` through
`invoke-interface` by one and the `invoke-*` `/range` variants by two. Values at or below `2c` and
from `7b` on carry one value in both versions. The values `77`–`7a` carry no instruction in
`009`; `013` assigns `77` and `78` to `invoke-static/range` and `invoke-interface/range` and leaves
`79`–`7a` unused.

### dex `009` / `013` instruction details

**`goto` and `goto/24`.** The narrow branch carries an 8-bit signed offset in code units, relative
to the instruction address. `goto/24` carries a 24-bit signed offset: the high eight bits in the
high byte of the first code unit and the low 16 bits in the second. The set has no 16-bit or 32-bit
`goto`, and an offset outside 24 signed bits cannot be encoded. (TODO: check whether a zero offset
is permitted for goto/24)

**The invoke shape (`34c`).** The argument-word count is a full byte in `AA` with the values
`0`–`4`; the four argument registers occupy the nibbles of the third code unit. A wide argument
takes two consecutive registers, and no more than four argument words fit. `execute-inline`,
`invoke-direct-empty`, `invoke-virtual-quick` and `invoke-super-quick` keep this shape, by using the
`34mi` and `34ms` formats; the range forms of the quick invokes use `3rms`.

**Predefined constants (`11p`).** `const/special` loads one of sixteen 32-bit constants selected by
the 4-bit index; `const-wide/special` loads the 64-bit entry at the same index into a register pair.
The table is listed with format `11p` in the instruction formats document.

**Typed array construction.** Eight `12x` instructions construct arrays of primitive components:
`new-array-boolean`, `new-array-byte`, `new-array-char`, `new-array-short`, `new-array-int`,
`new-array-long`, `new-array-float`, `new-array-double`. `new-array` (`22c`) takes a type index that
refers to the array's component type. Both forms take the array size in a register and store the
reference in a 4-bit destination register.

**Switches.** `packed-switch` and `sparse-switch` use `21t` and carry a 16-bit signed offset to
their payload table. Each payload target is a 16-bit signed offset relative to the address of the
switch instruction.

**The odex forms.** `execute-inline` indexes the inline-method table of built-in implementations.
The six quick field accesses carry the resolved byte offset of the instance field from the start of
the object in `CCCC`; the typed `iget` / `iput` variants use the six untyped opcodes.
`invoke-virtual-quick` indexes the receiver's vtable, `invoke-super-quick` the vtable of the current
method's class's superclass, and their range forms use `3rms`. `invoke-direct-empty` references a
direct method with an empty body – in practice `Object.<init>()V` – and does not perform the call.

**Instructions outside the set.** The set defines no `const/high16`, `const-wide/high16`,
`const-string/jumbo`, `goto/32`, `fill-array-data`, volatile field access,
`return-void-barrier`, `invoke-object-init/range`, `execute-inline/range` or
`throw-verification-error`.
